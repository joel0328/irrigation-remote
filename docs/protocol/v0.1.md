# Protocol v0.1

Status: **draft**. The portable firmware library implements this page and its host tests pass. It has never been sent over a radio. Expect breaking changes before 1.0.

## Scope

- One handheld paired with one receiver.
- The handheld starts a zone with a run time, stops the running zone, asks for status, and exchanges versions.
- The receiver acknowledges every valid command and reports what its outputs are doing.
- The radio layer (LoRa on 902 to 928 MHz is proposed, with spreading factor, bandwidth and channel plan to be chosen in Phase 1) carries each frame as one packet. Nothing here depends on the modulation.

## Frame

All multi-byte fields are little-endian.

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 1 | `ver` | `(MAJOR << 4) \| MINOR`. v0.1 is `0x01`. |
| 1 | 1 | `type` | Message type. Bit 7 set means the frame was sent by the receiver. |
| 2 | 4 | `net_id` | Pairing identifier shared by the handheld and its receiver. |
| 6 | 4 | `counter` | Sender's rolling counter for this direction. Never 0. |
| 10 | 1 | `len` | Payload length, 0 to 32. |
| 11 | `len` | payload | Depends on `type`. |
| 11 + `len` | 8 | `tag` | First 8 bytes of AES-128-CMAC over bytes 0 to 10 + `len`. |

The smallest frame is 19 bytes and the largest is 51.

The frame is authenticated, not encrypted. Anyone can read which zone was started; only a holder of the key can make a frame the receiver will act on. Encryption can be added in a later version if the friend's company wants it.

### Version check

While MAJOR is 0, a receiver accepts only frames whose `ver` byte equals its own. From 1.0 on, the MAJOR nibble must match.

### Direction

The direction bit in `type` is covered by the tag. A receiver drops frames with bit 7 set, and the handheld drops frames without it, so a frame cannot be reflected back to the device that sent it.

## Messages

| Type | Name | From | Payload |
|---|---|---|---|
| `0x01` | HELLO | handheld | `fw_major`, `fw_minor`, `fw_patch`, `fw_flags` (bit 0: dev build), 1 byte each |
| `0x02` | START | handheld | `zone` (u8, 1 to zone count), `minutes` (u16; 0 means the receiver's default) |
| `0x03` | STOP | handheld | none |
| `0x04` | STATUS_REQ | handheld | none |
| `0x81` | HELLO_REPLY | receiver | `fw_major`, `fw_minor`, `fw_patch`, `fw_flags`, `zone_count` |
| `0x82` | ACK | receiver | see below |

The protocol version is carried in every frame's `ver` byte, so HELLO does not repeat it.

### ACK payload (9 bytes)

| Offset | Size | Field | Meaning |
|---|---|---|---|
| 0 | 4 | `acked_counter` | Counter of the command this answers |
| 4 | 1 | `result` | 0 OK, 1 run time clamped, 2 bad zone, 3 bad payload, 4 unsupported type |
| 5 | 1 | `zone` | Zone that is on or about to come on, 0 if none |
| 6 | 2 | `remaining_s` | Seconds left in the run, rounded up |
| 8 | 1 | `sense` | Bit 0 zone output voltage seen, bit 1 master output voltage seen, bit 7 no sense reading available |

The `sense` bits are the tier 2 confirmation from the [architecture](../architecture.md). They mean "24 VAC is present on the output", not "water is flowing". Tier 3 (solenoid current) needs a later version.

## Receiver behaviour

1. Drop the frame without replying if the length, version, tag or `net_id` is wrong, or if the direction bit says it came from a receiver.
2. Check the counter:
    - greater than the last accepted: fresh, act on it;
    - equal to the last accepted, with the same tag: a retry of the same command, so re-send the previous reply and do not act again;
    - anything else: stale, drop it.
3. Act and reply with an ACK (or a HELLO_REPLY).

Run-timer rules (REQ-08 to REQ-10):

- One zone at a time. Starting a different zone turns all outputs off, waits a dead time (200 ms by default), then turns the new zone on. Its full run time starts after the dead time.
- Starting the zone that is already running restarts its timer with no off gap.
- Run time 0 means the default (20 minutes). Longer than the maximum (120 minutes) is clamped and the ACK says so.
- The run ends when the receiver's own timer runs out. No message is needed, so a lost link cannot leave a zone on.
- At power-up all outputs are off.

## Counters

- Each direction has its own counter. The handheld's counter numbers its commands; the receiver's numbers its replies.
- A sender must persist its next counter value before it transmits, so a reset never reuses a value. A practical way to spare flash is to reserve a block (say 64 values) at a time and skip to the next block after a reset.
- The receiver persists the last accepted counter. Only the counter is stored, not the tag, so the retry path does not survive a reset; a retry after a receiver reset is dropped and the handheld should send a fresh STATUS_REQ.
- When a counter reaches its maximum the pair must be re-keyed. At one command a second that takes more than 130 years.

## Handheld behaviour (proposed)

- After sending a command, wait for an ACK whose `acked_counter` matches. If none arrives within a timeout (to be set from Phase 1 latency measurements), re-send the identical frame up to a few times.
- Show the result to the user: acknowledged, acknowledged with zone voltage seen, or no answer.

## Known gaps in v0.1

- No pairing procedure (REQ-12). Keys and `net_id` are provisioned by hand for now.
- No key-management plan. The firmware's key is a placeholder.
- One receiver per handheld. TRC addresses up to 199 receivers per group code; a later version may add a receiver address.
- No program runs, only single zones.
- A version mismatch shows up only as "no reply", because frames with another `ver` byte are dropped before they are read. A later version should let HELLO and HELLO_REPLY through across versions, so the handheld can say which side needs an update.
- An 8-byte tag gives 64-bit forgery resistance per attempt, which is far beyond what a radio link can try. Revisit if the threat model changes.
